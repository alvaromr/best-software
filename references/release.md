# Versioning, build, release and deploy artifacts

**Goal:** every artifact is reproducible, traceable to one immutable version, and verified as the user receives it. A
deploy is boring: previewed, idempotent and reversible. This serves correctness, truth and safety.

Scope: the artifacts in the repo (version source, changelog, build and release scripts, Dockerfiles, compose, deploy
hooks, CI config files). Designing pipelines and workflows is out of scope.

## Practices

### Versioning
- **Keep the version in one place,** read by the build, mirrored automatically and computed by a script. *Why:* two
  version strings will eventually disagree (coherence).
- **Use SemVer against an explicitly defined public API,** and mark breaking changes. Use CalVer only for date-driven
  releases. *Why:* the version number is a promise to consumers about what an upgrade may break.
- **Keep a changelog** (Keep a Changelog, with `[Unreleased]` updated per user-visible change). Write it in user terms;
  release notes come from it and span from the previous release tag. *Why:* users need to know what changed for them,
  not which files moved.
- **Bump only when the build can no longer fail, and never deploy an untagged commit to production;** previews and
  staging may run any commit, and tags themselves follow `git.md`. *Why:* a version must identify exactly one
  artifact, forever, while a preview exists to try what is not released yet.

### Build
- **Make builds reproducible:**
  - lockfiles and the toolchain pin (`tooling.md`, "Dependencies")
  - base images pinned by digest
  - deterministic outputs
  - build from a clean tree at the tip of the release branch

  *Why:* only a reproducible build can be trusted, debugged and rebuilt after a disaster.
- **Script the release and make it fail-fast:**
  1. Bump.
  2. Run the gate on every supported version. A release is not a reason for a full mutation run (`testing.md`,
     "Coverage and mutation").
  3. Build.
  4. Publish to a test index or staging.
  5. Install it as a user would, in a clean environment, and smoke it.
  6. Publish.
  7. Tag.

  Its commits follow the repo's convention (`git.md`, "Messages"). Stop at the first failure, and never print
  credentials. Run the script dry, with nothing published, before the
  first tag. *Why:* manual releases skip steps under pressure, testing the installed artifact catches packaging errors
  that dev installs hide, and a script that has never run fails at its first real step, after the tag is out.
- **Verify the release build specifically:** minification and shrinking, signing, artifact contents. Compile debug
  tooling out of release. *Why:* release-only transformations break things debug builds never show, and debug tooling
  in release is an attack surface.
- **Ship only what is needed:** explicit package includes, typed markers, consumer shrinker rules inside
  libraries. Update sample apps in the same procedure. *Why:* consumers should need no extra setup, and samples that lag
  mislead.
- **Choose the artifact type by purpose** (store bundle vs QA package), and never run parallel builds of the same job
  that share an output or cache. *Why:* the wrong artifact gets rejected or shipped by mistake, and builds that share
  a destination race.

### Containers
- **Use multi-stage builds,** so build tools never reach the runtime image, and add a `test` stage that runs the gate.
  *Why:* a smaller image means a smaller attack surface, and an image that fails its tests is never produced.
- **Run as non-root, with a `HEALTHCHECK` and a slim image.** *Why:* this limits the damage of a compromise and lets the
  orchestrator see real health.
- **Order layers for the cache:** dependencies before source. *Why:* rebuilds stay fast.
- **Stamp the version, tag images with the git SHA, and fail compose on missing variables (`${VAR:?}`).** *Why:* every
  running container is traceable, and a misconfiguration fails at start, not at first use.

### Deploy
- **Use the same artifacts in dev and prod;** only the environment differs (12-factor). Keep a local production-like
  rehearsal. *Why:* environment differences are where "it worked locally" dies.
- **Show a preview before any deploy:** what it will restart, migrate or wipe. *Why:* surprises in production are
  incidents.
- **Make deploys idempotent:** no change means no restart, and data reloads only when its source changed. *Why:*
  re-running must be safe, and needless restarts are needless downtime.
- **Make deploys reversible,** with a documented rollback. *Why:* every deploy can fail, and the way back must already
  exist.
- **Database migrations go forward only:**
  - A migration that has run in a shared environment is immutable; fix it with a new one.
  - Migrations alone own the schema.
  - Review autogenerated migrations before running them.

  *Why:* an edited migration diverges from what production actually ran.
- **Verify the deploy actually landed:** the new version is served or installed, and the old credential or cache is
  gone. *Why:* a green pipeline can still serve the old artifact.
- **Expose a version endpoint in a service, beside its health endpoint (`operability.md`, "Observability"), and
  provide a smoke task.** *Why:* "which version is running, and is it OK?" must have a one-command answer.
- **Document disaster recovery:**
  - Rebuild from scratch.
  - Back up secrets outside the repo.
  - Keep a cold bundle of the full history.

  *Why:* recovery is needed exactly when the people and tools that know it are unavailable.
- **Redirect the URLs a rewrite moves;** never leave them to 404. *Why:* links and search rankings outlive rewrites.
- **Audit platform deadlines early,** in a recreatable document. *Why:* store and runtime deadlines do not move.

## Judgment
- Choose the distribution channel by cost and requirements, and record the decision.

## Audit signals
- The version in several places. `changeability`
- No changelog. `changeability`
- `latest` images. `correctness`
- Dev tools in the runtime image. `safety`
- A container running as root. `safety`
- Deploys that always restart. `correctness`
- A manual-only release. `correctness`
- Edited migrations. `correctness`
- A service with no version endpoint. `correctness`
